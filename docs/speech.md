# 15分钟带你开发一个智能体

> 时长约 15-20 分钟。配合站点 site/index.html 演示。
> 括号内为动作提示，不需要念出来。
> 粗体为强调语气。

---

## 开场

大家好。今天我想用十五分钟，带你们从头走一遍：一个智能体到底是怎么工作的。

把一个智能体的每个零件拆开来看，装起来，让它跑一遍。

先问一个问题：你觉得什么是智能体？

（停顿两秒）

其实没那么玄乎。智能体就是"一个模型 + 能干活的手"。模型负责想，工具负责做。就这么简单。

## 模型本身是孙膑

我给你们打个比方。

你们知道孙膑吧？腿脚不方便的军师，脑子特别好使，但他自己动不了。他要指挥外面的士兵帮他跑腿、帮他打仗。

模型也是这样。

（指屏幕）

你看这个页面，最开始的循环只有三行：用户问题，模型判断，输出回答。模型就是一个大脑，但它碰不到外面任何东西。

那要让它能干活怎么办？给它接上工具。像给孙膑装上义肢，装上一个望远镜，装上一个传声筒。每一个工具，都是模型向外伸出去的一只手脚、一只眼睛、一只耳朵。

## 工具循环 -- 智能体的心脏

（切到工具循环章节）

加一个工具之后，循环就变了：模型先判断要不要用工具。要用，就发出调用，系统执行，拿到结果，喂回给模型。模型再判断，再决定是继续还是回答。

这个循环是整个智能体最核心的东西。你往后的所有东西 -- 记忆、上下文、计划、子代理 -- 都是长在这个循环上面的。

（指流程图）

你们看这个分支结构：调还是不调？调了就回来继续，不调就输出回答。就这么简单。但这个简单的循环，是所有智能体的起点。

## 为什么需要记忆

（切到记忆章节）

现在有个问题。模型每一次调用，上下文是独立送的。它不会天然记住上一轮干了什么。

好比你跟一个人说话，你说完一句，他就失忆了，你下一句还得从头开始。这不行。

所以我们需要短期记忆。每一轮结束后，我们把这一轮干了什么、工具查到了什么、模型回答了什么叫记下来。下一轮再喂回去。

（指例子）

你看这个例子：用户说帮我看看项目干什么的。模型调了三个工具，读 README、读 spec、跑测试。这一轮结束，session 记住了调用过什么、结果是什么、活跃文件是什么。

下一轮用户再说"帮我把 README 重写一下"，模型就知道：哦，我知道这个项目是干什么的。

## 长期记忆 -- 放久的规则

（切到长期记忆章节）

短期记忆记的是当前会话里的事。那如果有一个规则，是这个项目长期都遵守的呢？比如"先看事实，再做判断"。

你不能每轮都跟模型说一遍。你需要长期记忆。

长期记忆就是放在项目里的固定规则和做法。在 Kitty 里，它来自两个东西：AGENTS.md 是项目的工作规则，skills 是已经试过的熟练做法。

（指西红柿炒鸡蛋例子）

你看这个 skill，就像一份菜谱。厨房里挂着一排菜谱，模型看到"西红柿炒鸡蛋"这个菜名，就自己去加载那份菜谱，按上面的做法来。不用每次从零想。

## 上下文装配 -- 所有零件拼在一起

（切到上下文装配章节）

现在我们把东西拼起来。

每一轮真正发给模型的，是一个大包裹。里面有系统提示词、人格设定、短期记忆、长期记忆、可用工具列表，再加上用户这次的输入。

（指例子）

你看这个具体例子。六块积木摆出来，系统把它们拼成一段话，发给模型。模型拿到这段话，就知道自己的身份、当前项目状态、这个项目的规则、有什么工具可以用、用户现在要什么。

这一段话就是模型这一轮的全部世界。我们要保证这个世界信息是完整的。

## 对话太长怎么办

（切到压缩章节）

聊多了之后会有一个现实问题。模型上下文窗口是有限的。

就像一张纸，写满就不能再写了。怎么办？把前面的事整理成摘要。早期对话压成一段总结，保留最近几轮的完整内容，再接上当前用户输入。模型既有全局感，又能处理眼前的事。

## 做计划

（切到计划章节）

复杂任务来了。比如做一盘西红柿炒鸡蛋。有好几个步骤，谁先谁后有顺序。

模型会先做一个 To Do 列表，把每一步写清楚。然后从第一步开始，一次只做一步。第一步完成标 [x]，第二步才变成进行中。

（指例子）

这个设计看起来简单，但它解决了一个大问题：模型不会因为一次跑偏就把整个任务搞乱。每一步都有明确的状态，中断了也知道从哪里恢复。

## 子代理 -- 分身

（切到子代理章节）

最后一个零件是子代理。刚才说的所有东西，都是在一个上下文里完成的。但如果我们需要同时查两件不同的事呢？或者有一件独立的事，不想让它把主上下文的空间挤占掉？

子代理就是另一个独立工作的 agent。主 agent 给它一个明确目标、一个边界、一个期望结果，它带着自己的上下文和工具去完成任务，最后只把结论交回来。

（指例子）

你看，主 agent 在做菜，突然需要确认客人有没有忌口。这件事跟上菜谱没有关系，不需要让主 agent 的上下文被这些资料占掉。交给子代理。子代理查完，说"没有额外忌口"，就完了。中间的过程、工具调用、判断，都留在子代理自己的上下文里。

这里特别说一下，跟历史压缩的区别：压缩解决的是时间太长的问题，子代理解决的是任务分支的问题。两个都在保护上下文的专注力。

## 走一遍完整的例子

（切到 cycle 可视化页面）

好，前面讲了七个零件。现在看它们怎么一起工作。

我们回到西红柿炒鸡蛋这个例子。

（点击各个步骤演示）

第一步，用户说"做一盘西红柿炒鸡蛋"。模型判断，查到食材清单。

第二步，模型需要做法，调用 skill 加载西红柿炒鸡蛋的菜谱。

第三步，短期记忆把食材和菜谱记下来。长期记忆提供项目规则。

第四步，需要查客人忌口，派子代理去。子代理独立查完，回来报告。

第五步，用户又说"鸡蛋再嫩一点，少放糖"。这时上下文装配把上面所有信息拼成一段话发给模型。

第六步，模型拆成三步计划：处理鸡蛋、炒西红柿、合锅收味。

每一步执行完，更新 To Do 列表。最后一步完成，端上一盘西红柿炒鸡蛋。

（停顿）

你们注意看这个 cycle 动画上的游标。它在节点之间转一圈，就对应了模型的一次完整思考-决策-行动-观察的循环。整个过程，每一个模块都在协同工作。

## 收尾

好，十五分钟到了。我 fast forward 一下，总结今天说了什么。

一个智能体，本质上就是：

一个循环 -- 工具循环，这是心脏。
两种记忆 -- 短期记会话，长期记规则。
一次装配 -- 每轮把信息拼成模型能理解的上下文。
两种保护机制 -- 压缩保护上下文长度，子代理保护上下文专注力。
一个计划系统 -- 把复杂任务拆成可执行的步骤。

这些东西合在一起，就是一个能持续工作的智能体。

如果你有兴趣，这个项目在 GitHub 上是开源的。扫码或者点右上角 GitHub 链接就能看到完整源码。你也可以直接 npm install 安装试一试。

谢谢大家。
