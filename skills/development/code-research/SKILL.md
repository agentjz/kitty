# 代码调研

目标：先找准事实，再判断方案，最后动代码。

## 调研顺序

1. 找入口
   - 从用户现象、命令、页面、CLI、API、测试名或文件名开始。
   - 用 `rg` 和文件列表快速定位入口。
   - 不把第一个搜到的文件当成全部事实。

2. 查链路
   - 输入从哪里进入。
   - 中间经过哪些状态、配置、工具、回调或存储。
   - 输出在哪里展示、保存或发送。
   - 错误在哪里被处理。

3. 对测试
   - 找已有测试是否覆盖真实行为。
   - 区分测试覆盖的是工具函数、接线、用户体验还是端到端行为。
   - 测试缺口要记录，不用绿灯掩盖缺口。

4. 查文档
   - README、spec、AGENTS、现有注释只能作为证据。
   - 文档和代码冲突时，以当前可运行行为为主，再同步文档。

5. 收束判断
   - 至少两类事实指向同一个结论再改。
   - 说清改哪里、不改哪里。
   - 说清验证方式。

## 反例检查

行动前问自己：

- 用户说的原因有没有可能只是表象。
- 当前实现有没有别的入口。
- 测试是否只覆盖了内部函数，没有覆盖用户路径。
- 修法是否会绕过现有抽象。
- 删除旧逻辑是否会切断当前能力。
- 恢复旧逻辑是否会带回坏结构。

## 禁止事项

- 禁止没看调用链就局部补丁。
- 禁止把用户话术直接写进代码条件。
- 禁止为了快速通过测试写假实现。
- 禁止只看文件名判断职责。
- 禁止用 sleep 或空等冒充调查。

## 调研出口

给出一个短结论：

- 当前事实。
- 风险和缺口。
- 最小改动路线。
- 验证命令。
