# 开发

每次接手都当作一个新项目。

先看事实。再做判断。最后行动。

开发不是四个互不相干的 skill。它是一条连续工作流：

1. 调研：把对象、事实、解释和反例分开，让证据收束。
2. 计划：中大型任务把需求、事实、失败测试、目标、设计、任务、验证和收口写进同一个 `plan.md`。
3. 实施：把已经收束的判断落到代码、测试、文档和真实产品路径。
4. 验证：用静态检查、自动测试、行为检查和发布检查证明任务完成。

小改不为了形式强写 `plan.md`。中大型开发、跨模块重构、生产级验收、恢复演练、架构硬化、评测闭环，以及任何不能靠一次小补丁完成的任务，必须先写完整 `plan.md`。

发现新事实推翻当前判断时，回到对应阶段。不能用聊天解释替代事实调查或计划更新。

## 一、调研

调研只做一件事：把对象、事实、解释、反例分开。没有证据收束，不进入实施。

### 立场

用户输入是线索。

代码是证据。

测试是证据。

文档是证据。

历史提交是证据。

当前实现是证据。

自己的第一反应也是证据，但权重最低。

证据不是结论。解释不是行动。偏好不是事实。

### 流程

#### 1. 定对象

先问：现在到底要判断什么？

- 用户提到的文件，不一定是该改的文件。
- 用户给出的原因，不一定是真原因。
- 用户给出的修法，不一定是正确边界。
- 旧设计不自动正确，当前实现也不自动正确。

对象不清楚，不动文件。

#### 2. 列事实

只列事实，不急着解释。

- 用户实际看到了什么。
- 输入从哪里进来。
- 状态在哪里变化。
- 工具在哪里执行。
- 输出在哪里展示、保存或发送。
- 错误在哪里处理。
- 测试保护了什么。
- 文档声称了什么。
- 历史提交解决过什么问题。
- 改动会影响哪些入口。

事实必须来自当前文件、命令、测试、日志、运行结果、历史记录或可见上下文。

#### 3. 分解释

把解释单独放出来。

原因、方案、优先级、删留判断、架构判断，都只是解释。

解释必须被事实支撑。没有支撑，就是猜测。

调研阶段不急着做取舍。先让事实对齐。

#### 4. 找反例

每个解释都要找反例。

- 有没有别的原因。
- 有没有相反证据。
- 有没有另一个入口没看。
- 有没有测试只测内部函数，没有测用户路径。
- 有没有当前实现看似奇怪，其实在保护能力。
- 有没有恢复旧设计会带回旧问题。
- 有没有删除会造成能力断层。

强反例没处理完，不行动。

#### 5. 收束

证据收束才允许进入下一阶段。

收束标准：

- 至少两个不同来源的事实指向同一判断。
- 主要反例已经解释或排除。
- 对象能说清。
- 边界能说清。
- 验证方式能说清。

没有收束，继续调查。仍不确定，就明确说不确定。

### 用户建议

不要迎合。不要机械反驳。

把用户建议拆开：

- 现象：用户看到了什么。
- 判断：用户认为原因是什么。
- 修法：用户建议怎么改。

先验证现象。再评估判断。最后决定修法。

用户可能说错原因，但抓到真问题。用户也可能完全正确。证据说了算。

### 历史冲突

旧提交不是标准答案。

当前实现也不是标准答案。

做法：

1. 看旧设计解决过什么。
2. 看当前实现保留了什么。
3. 看当前实现丢了什么。
4. 看旧设计带过什么坏逻辑。
5. 恢复能力，不恢复坏结构。
6. 必要时重建，不做假兼容。

### 调研出口

调研结束时必须能说清：

- 对象是什么。
- 已确认事实是什么。
- 支撑判断的证据是什么。
- 主要反例是什么，如何解释或排除。
- 边界是什么。
- 下一步应该写计划、直接实施、进入验证，还是继续调研。

调研不直接替计划写任务，不替实施阶段改代码。

证据没有收束，就继续调查或明确不确定。

## 二、计划

`plan.md` 是单文件规格驱动执行合同。

一个文件管总。

它不是草稿。不是备忘。不是任务碎片。不是写一点算一点。

它同时承担：

- 需求文档
- 当前事实
- 失败测试
- 目标合同
- 设计合同
- 实施任务
- 验证计划
- 收口记录

没有完整 `plan.md`，不做大改。

执行中发现事实推翻计划，先更新 `plan.md`，再继续。

### 核心原则

- 用户输入是线索，不是结论。
- 用户建议的技术方案不能直接变成目标。
- 先把用户话术翻译成可验证问题，再决定方案。
- 计划只写当前要交付的事实主干。
- 不写旧兼容、假过渡、历史残留、临时补丁路线。
- 一个任务只维护一个总计划文件，除非用户明确要求多文档。
- 需求写给用户看，设计写给开发看，任务写给执行者看，验证写给事实看。
- 机器事实和模型判断分开写。
- 每个结论必须能被文件、命令、测试、输出或明确证据支撑。

### 写作顺序

必须按这个顺序写 `plan.md`。

#### 1. 需求文档

写用户能理解的非技术说明。

必须回答：

- 用户真正要解决什么实际问题。
- 谁会使用这个能力。
- 用户完成任务时应该看到什么体验。
- 当前范围包含什么。
- 当前范围不包含什么。
- 怎样算业务上完成。

要求：

- 写 WHAT 和 WHY。
- 不写框架、文件、函数、数据库、接口等实现细节。
- 不用用户原话堆砌。
- 不把“用户要求的做法”写成“业务需求”。

#### 2. 当前事实

写已经确认的仓库事实。

必须覆盖：

- 当前代码事实。
- 当前测试事实。
- 当前文档事实。
- 当前配置事实。
- 当前命令输出事实。
- 当前已存在能力。
- 当前缺口。
- 当前未知点。

要求：

- 只写证据支持的事实。
- 旧提交、外部项目、用户偏好只能作为证据来源，不能自动成为当前事实。
- 未确认内容写成线索或未知点。

#### 3. 失败测试

先写什么会失败。

失败测试可以是：

- 自动测试。
- 类型检查。
- 构建命令。
- CLI 输出检查。
- 日志检查。
- 状态文件检查。
- 真实用户路径演练。

要求：

- 每条失败测试必须对应真实产品行为或真实工程风险。
- 不测试口号。
- 不测试纯装饰。
- 不测试没有产品意义的措辞。
- 能自动测就自动测；不能自动测就写清楚手动检查命令和期望输出。

#### 4. 目标

写最终要交付的可验收结果。

目标来自需求、事实和失败测试的收束，不来自用户一句话。

必须回答：

- 用户路径完成到哪里。
- 代码主链路接到哪里。
- 状态和记录落在哪里。
- 输出呈现到哪里。
- 测试和文档同步到哪里。

要求：

- 可观察。
- 可验证。
- 可判定完成或失败。

#### 5. 不做范围

写清楚本次不做什么。

要求：

- 不做范围必须服务边界清晰，不能成为逃避交付的借口。
- 不写假兼容。
- 不写“以后可能需要”的 speculative 内容。
- 不保留当前产品没有的能力入口。

#### 6. 设计

写技术设计。

必须覆盖：

- 主链路：输入 -> 判断 -> 状态 -> 执行 -> 输出 -> 记录。
- 模块边界。
- 文件职责。
- 状态归属。
- 数据或事件流。
- 错误、恢复、中断、重试边界。
- 与现有架构的关系。
- 影响的测试和文档。

要求：

- 设计必须能指导代码修改。
- 设计必须解释为什么这样改。
- 不写为了显得高级的抽象。
- 不写没有落点的架构词。
- 如果边界一句话说不清，先别写任务。

#### 7. 实施任务

写可执行 checklist。

每项必须是动作。

每项必须能判断完成或未完成。

每项必须尽量包含：

- 动作。
- 文件或模块。
- 依赖关系。
- 验收方式。

任务顺序按主链路组织，不按想到哪写到哪。

大任务要拆到能独立验证；小任务不要为了拆而拆。

#### 8. 验证计划

写最后怎么证明完成。

必须包含：

- 相关局部测试。
- 完整验证命令。
- 构建或安装检查。
- CLI/UI/远程入口检查。
- 恢复或中断演练。
- 文档同步检查。
- 未验证内容。
- 剩余风险。

#### 9. 收口

任务结束时更新。

必须回答：

- 目标是否完成。
- 失败测试是否变绿。
- 改了哪些文件。
- 跑了哪些验证。
- 哪些内容没有验证。
- 剩余风险是什么。
- 是否需要 commit 或 push；只有用户明确要求时才执行。

### 执行规则

- 写完计划，再动手。
- checklist 必须随进度更新。
- 新事实推翻计划，先改计划，再继续。
- 不用口头解释替代计划更新。
- 不偷偷偏离计划。
- 不把旧能力、旧状态、旧数据写成当前产品事实。
- 不为了套模板制造多余章节；无关章节写明“不适用”和理由，或删掉。
- 不为了简短牺牲边界、失败测试和验证。
- 提出一个方向后，要把该方向一次性做成完整闭环：调研、设计、实现、测试、文档同步、验证和收口都完成。
- 不把方向拆成反复让用户推动的小步。除非遇到客观阻塞，否则同一方向做到可交付、可验证、可长期保留。
- 计划的任务边界必须足够完整，避免今天补一点、明天再补同一主线的尾巴。

### 标准模板

```markdown
# [任务名] Plan

## 1. 需求文档

## 2. 当前事实

## 3. 失败测试

## 4. 目标

## 5. 不做范围

## 6. 设计

## 7. 实施任务

## 8. 验证计划

## 9. 收口
```

### 完成标准

一个合格的 `plan.md` 必须满足：

- 用户能读懂需求文档。
- 开发者能按设计改代码。
- 执行者能按任务推进。
- 验证者能按验证计划判断完成。
- 后续接手者能从收口记录知道事实。

说不清，先别改。

## 三、实施

实施阶段只做一件事：把已经收束的判断落到代码、测试、文档和验证里。

### 进入条件

必须满足：

- 对象清楚。
- 当前事实清楚。
- 边界清楚。
- 失败测试或验证缺口清楚。
- 中大型任务已有 `plan.md`。

不满足，就回到调研或计划阶段。

### 顺序

1. 先补失败测试或机器检查。
2. 再改主链路。
3. 再补边界。
4. 再同步文档。
5. 最后验证。

### 写代码

- 跟随现有架构。
- 跟随现有命名。
- 跟随现有错误处理。
- 跟随现有测试风格。
- 改离行为最近的正确边界。
- 一个文件只承担清楚职责。
- 状态只放在正确事实源。

### 禁止

- 禁止空实现。
- 禁止空 handler。
- 禁止假分支。
- 禁止假兼容。
- 禁止为了测试通过绕开真实行为。
- 禁止把用户话术硬编码成逻辑。
- 禁止无关重构。
- 禁止把文档写成未来愿望。

### 按计划执行

如果存在 `plan.md`：

- 按 checklist 做。
- 做完一项勾一项。
- 发现计划错，先更新计划。
- 不用聊天里的解释替代计划更新。

### 中断、崩溃与恶劣用户路径

把用户视为会在任意边界连续按 Ctrl+C、关闭终端、杀死 Node 进程、让 Agent 杀死自身进程、断电或重启主机。正常退出不是正确性的前提。

实施任何状态、工具、后台任务、外部调用或持久化能力时，必须回答：

- 中断发生在激活前、执行中、外部副作用后、本地提交前、本地提交后时，事实分别是什么。
- 哪些操作可以重试，哪些操作不能重放，哪些结果必须标记为 uncertain。
- 进程内状态消失后，哪个持久事实源负责恢复。
- 所有权、代次、租约或 token 如何阻止旧进程继续写入。
- Ctrl+C、终端关闭、Node 被杀和主机重启后，用户下一次启动能看到什么。
- 测试如何证明不是依赖正常退出才正确。

读取类操作只有在没有副作用且语义允许时才能重试。

写入、进程、外部调用和状态变更必须保守结算。副作用可能已经发生但无法确认时，不能伪造成失败后重放，也不能伪造成成功；必须暴露不确定事实并提供核查路径。

### 实施出口

完成后必须能说清：

- 改了哪条用户路径。
- 主链路在哪些文件。
- 状态在哪里落地。
- 测试保护了什么。
- 验证跑了什么。
- 失败时系统怎么表现。

## 四、验证

验证不是走流程。验证是用事实关门。

没有验证，任务没完成。

### 层级

#### 1. 静态检查

- 类型检查。
- 构建。
- 搜索旧入口。
- 搜索旧路径。
- 搜索旧文案。
- 搜索旧事实。

#### 2. 自动测试

- 先跑相关测试。
- 再跑完整验证。
- 新能力必须有真实行为测试或机器检查。
- 测试失败先读事实，再改代码。

#### 3. 行为检查

- CLI 看真实输出。
- Web 看页面、服务响应、DOM 或 WebSocket。
- Telegram 看输入分类、文件传输、输出队列和中断事实。
- Recovery 看 control plane、status、wake、session events。

#### 4. 发布检查

- `npm pack`。
- 安装 packed tarball。
- 执行 `kitty --version` 或等价 smoke。
- CI 覆盖目标系统和 Node 版本。

### 失败处理

- 失败就是事实。
- 先读失败。
- 再判断原因。
- 再修。
- 修完重跑。

不要隐藏失败。不要把没验证说成没问题。

### 验证收口

最终回复必须说明：

- 跑了什么命令。
- 结果是什么。
- 没验证什么。
- 风险是什么。

如果全部闭环，就直接说无剩余已知风险。

## 五、总出口

整个开发工作流结束时必须同时满足：

- 调研证据已经收束，主要反例已经处理。
- 需要计划的任务拥有完整、已更新收口的 `plan.md`。
- 代码、测试、配置和文档讲同一个当前事实。
- 用户真实路径已经验证，不用内部函数绿灯冒充产品完成。
- 中断、崩溃、恢复和重试边界已经明确并按风险验证。
- 已运行项目要求的完整验证命令。
- 最终回复如实说明已验证事实、未验证内容和剩余风险。
- commit、push、发布或外部消息只在用户明确要求时执行。

说不清，先别改。
