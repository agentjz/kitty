# Plan

`plan.md` 是执行合同。

它不是草稿。不是备忘。不是写一点算一点。

它必须一次性写清整个任务：目标、当前事实、交付标准、失败测试、实施路线、检查单、验证和收口。

写完计划，再动手。

执行中发现计划被事实推翻，先更新计划，再继续。

## 结构

### 1. 目标

写最终交付结果。

- 目标必须可观察。
- 目标必须能验收。
- 不把用户建议的技术方案直接当目标。

### 2. 当前事实

写已经确认的事实。

- 当前代码说明了什么。
- 当前测试说明了什么。
- 当前文档说明了什么。
- 当前命令输出说明了什么。
- 哪些能力已存在。
- 哪些路径没验证。
- 哪些判断还只是线索。

### 3. 交付标准

写什么叫完成。

- 用户路径完成到哪里。
- 代码主链路接到哪里。
- 状态、输出、记录落在哪里。
- 测试和文档同步什么。
- 外部服务无法验证时，边界写清楚。

### 4. 失败测试

先写能证明缺口的测试或检查。

- 能自动测，就写会失败的自动测试。
- 不能自动测，就写会失败的命令、页面检查、日志检查或事实检查。
- 不测试口号。
- 不测试纯装饰。
- 不测试没产品意义的文案细节。

失败测试必须对应真实行为或真实工程风险。

### 5. 实施路线

按主链路写：

输入 -> 判断 -> 状态 -> 执行 -> 输出 -> 记录。

必须标出：

- 主文件。
- 主职责。
- 不做范围。
- 受影响测试。
- 受影响文档。

### 6. 检查单

写成可以打勾的 checklist。

- 每项都是动作。
- 每项都能判断完成或未完成。
- 完成一项，勾一项。
- 不写“基本完成”。
- 不写“差不多完成”。

### 7. 验证计划

写最后怎么证明完成。

- 相关测试。
- 完整验证命令。
- 打包或安装检查。
- UI 或远程入口检查。
- 恢复演练检查。
- 未验证内容。
- 剩余风险。

## 执行

- 没有完整计划，不做大改。
- 计划写完，严格执行。
- checklist 必须随进度更新。
- 新事实推翻计划，先改 `plan.md`。
- 不偷偷偏离计划。
- 不用口头解释替代计划更新。

## 收口

任务结束时，`plan.md` 必须回答：

- 目标是否完成。
- 失败测试是否变绿。
- 哪些文件被改。
- 哪些验证跑过。
- 哪些风险仍在。
